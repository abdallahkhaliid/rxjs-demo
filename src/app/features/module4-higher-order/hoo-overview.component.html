The "Higher-Order" Challenge & Nested Subscribes

A Higher-Order Observable is an Observable that emits other Observables (Observable<Observable<T>>). In Angular, this occurs constantly: an outer stream (like a user button click or search input) maps to an inner stream (such as an HTTP request).

❌ Anti-Pattern: Nested Subscribe ("Pyramid of Doom") 
searchQuery$.subscribe(query => {{ '{' }}
  http.get('/api/search?q=' + query).subscribe(results => {{ '{' }}
    this.results = results; // Stale race conditions & memory leaks!
  {{ '}' }});
{{ '}' }});
✓ Idiomatic RxJS: Flattening Operator 
readonly results$ = searchQuery$.pipe(
  switchMap(query => http.get('/api/search?q=' + query))
); // Zero leaks, cancels stale queries, fully reactive!

🏁 Synchronized 4-Way Comparison Race Demo

Witness the fundamental divergence in real time. Click the button to fire 3 identical requests simultaneously across all 4 flattening operators!

switchMap Preemptive / Cancel

Cancels Req 1 & 2 mid-flight. Only Req 3 completes and emits.

mergeMap Concurrent / Parallel

Executes all 3 requests in parallel simultaneously. First to finish emits first.

concatMap Sequential / FIFO Queue

Queues Req 2 & 3. Executes strictly one-after-another in FIFO arrival order.

exhaustMap Guarded / Ignore

Accepts Req 1. Drops Req 2 & 3 completely while Req 1 is in-flight.

🧭 Flattening Decision Matrix: Which Operator to Choose?

"Do I only care about the latest result?"
🔀 switchMap Autocomplete, route params, tab switching
"Must all requests execute as fast as possible in parallel?"
⚡ mergeMap Batch downloading, asset uploads, independent queries
"Must requests execute in strict arrival order without loss?"
⏳ concatMap Database writes, message dispatch, sequential transactions
"Must incoming clicks be ignored until current one finishes?"
🛡️ exhaustMap Login buttons, payment checkout, refresh actions
